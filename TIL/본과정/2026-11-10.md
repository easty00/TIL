## 1. 무엇을 만들까 (기획 상의)
**한 일**
1. 각자 기획을 1개씩 가져와 투표했다. LLM 챗봇이 선정됐고, 정보 공유 커뮤니티를 더하기로 했다.
2. 기능 이야기를 하다 보니 기능정의서·스키마·프로젝트 개요를 문서로 정리해야겠다고 느껴, AI에게 준비 순서와 틀을 받았다.
3. AI가 채워 준 표는 최소한만 남기고 지웠다. 팀원들과 다 같이 채우려고 구글 드라이브로 스프레드시트를 공유했다.
4. 스키마·API 이야기를 하다 강사님 조언을 받아, 파트를 먼저 나누고 파트별로 논의한 뒤 다시 모이기로 했다.
5. 1시 전체 공유 때 말로만 설명하니 서로 상상이 안 가서 두루뭉술해졌다. 파트별 기능 정의로 AI 목업을 만들어 공유했고, 몇몇 팀원분이 방향을 잡으신 듯했다.
6. 2시 30분 다시 모였을 때는 다들 방향이 정해져 보였지만, 스키마와 기능정의서는 여전히 비어 있었다.

## 2. 어떻게 나눌까 (역할·협업 규칙)
**한 일**
1. 파트를 **회원가입&로그인 / 채팅 / 커뮤니티**로 나눴다. 나는 채팅에서 바꿔 회원가입&로그인을 맡았다.
2. 같은 파트 팀원과 디스코드에서 음성·화면 공유로 기능을 나눴다. 로그인, 소셜 로그인, 회원가입, 소셜 회원가입, 마이페이지로 나누고 그 안의 파츠를 상세히 나눈 뒤 중요도를 3단계로 매겼다.
3. 기능정의서 초안은 로그인, 회원가입, 마이페이지로 정리했다. 마이페이지는 다른 분이 맡으셨고, 여행 일정이 있어 한 페이지를 구현해 보시기로 했다.
4. 협업 툴은 스프레드시트, 디스코드, 줌을 쓴다.
5. 파트별로 브랜치를 내어 작업하고, develop에 합칠 때는 PR로 한다.

## 3. 첫 코드 (3시 40분~)

### 9시 : 주제 정하기
- 기획은 각자 1개씩 생각해 갔다. 내가 생각한 건 다음과 같다.
  ```markdown
  [주제] 같이 하는 습관 모임 앱
  강아지 산책, 러닝, 요리처럼 매일 반복하는 활동을
  정해진 시간에 같은 방 사람들과 함께 인증하는 모임 앱

  - 목적은 '꾸준함'. 뉴비가 고인물·터줏대감 때문에 이탈하지 않도록
    공개 방은 어느 방에 들어가는지 모른 채 랜덤으로 입장
  - 앱 홈에는 취미별 버튼만 있고, 누르면 그 시간대의 인증방 중
    아무 방에나 들어감
  - 홈 하단에 꾸준한 사람 랭킹(전체·분야별) 표시

  [핵심 기능]
  1. 활동별 모임방 + 실시간 채팅
     [고정 소모임]
     [소모임 활동 규칙] (주 1회 이상 참여 권장)
  2. 정해진 시간에 카메라 인증샷 올리기 + 모임 기록
  3. 프로필 페이지
  4. 꾸준함 뱃지 + 랭킹
  5. 그 외 기타 기능

  [나중에 시간 되면]
  - 영상 인증, 실시간 영상 공유 (줌이나 디스코드처럼)
  - AI가 모임 기록·채팅을 요약해 주는 기능 (선생님 LLM API 활용 가능한지 확인)
  - 음성 기능: 운동 중엔 타자 치기 어려우니
    말하면 텍스트로 변환(STT), 채팅을 읽어 주기(TTS)
  - 부적절하거나 방 목적에 맞지 않는 행동을 탐지해 경고장 주기
    · 채팅 글 → AI(LLM)로 탐지
    · 인증샷·영상 → YOLO로 탐지
    · 회원 신고도 받음
  - 사유 등록 요청을 이메일·카카오톡으로 보내기
  ```
- 투표 결과 다른 팀원이 생각한 **LLM 챗봇**이 선정되었다. 챗봇만으로는 기능이 부족해서, 여기에 **정보 공유 커뮤니티**를 더해 배운 것을 구현하기로 했다.
- 기술 스택 : Next.js, MongoDB, 프리즈마, Figma
- 백엔드 : 프론트엔드에 집중하라는 뜻에서, API가 필요하면 요청할 때 강사님이 직접 만들어 주시기로 했다. 기존에 가지고 계시던 API 모음(Swagger)도 공유해 주셨다.
- 스켈레톤 코드를 먼저 만들고, 슬래시, 오쓰, 타입 등을 미리 만들어 두고 시작하는 게 맞다는 이야기를 팀원분들이 하셨다.
- 💭 이전 팀플은 속도감이 있었거나, 정말 몰라서 무에서 유를 창조했었다. 이번엔 비슷한 분들(..이라기엔 나보다 배경지식이 출중한 분들이셨다)과 좀 더 제대로 된 프로젝트를, 그것도 8명이라는 대인원으로 하는 건 처음이다. 처음 듣는 용어는 아니지만 아직 어색한 용어를 많이 들어서 조금 어렵다는 기분을 느꼈다.

### 10시 : 문서 틀 잡기와 파트 나누기

- 필요한 기능을 이야기하다 보니 제대로 된 정리가 필요하다고 느꼈다. 기능정의서, 스키마, 프로젝트 개요 등을 다 같이 문서로 확실히 정리하면 좋겠다고 판단해 AI에게 틀을 요청했다.
- AI에게 받은 조언
  ```
  시작 전에 준비할 것 (이 순서대로)

  1. 한 줄 정의와 MVP 범위

  예: "로그인해서 GPT와 대화하고, 대화가 저장되며, 벨로그처럼 글을 쓰고 댓글·좋아요를 남길 수 있는 서비스"
  기능을 필수 / 있으면 좋음으로 나누세요. 채팅 + 회원가입은 필수, 이전 대화 기억 같은 것은 있으면 좋음으로 둘 수 있어요.

  2. 데이터 설계 (MongoDB 컬렉션)
  메모의 "유저 / 게시판 / 댓글 / 좋아요 / 챗지피티"를 컬렉션으로 풀면 이렇습니다.

  users: 이메일, 비밀번호(해시), 닉네임
  posts: 작성자, 제목, 내용, 작성일
  comments: 어느 글인지, 작성자, 내용
  likes: 어느 글인지, 누가 (같은 사람이 중복으로 못 누르게)
  chats: 대화방, 누구 것인지, 제목
  messages: 어느 대화방인지, 역할(user/assistant), 내용

  3. 페이지와 API 목록
  화면(로그인, 글 목록, 글 상세, 글쓰기, 채팅)과 각 화면이 부르는 API를 표로 적어둡니다. 이게 있으면 팀원끼리 "누가 뭘 만드는지"가 바로 나뉩니다.

  4. 기술 결정 (메모에서 이미 반쯤 답이 나온 것들)

  채팅 저장은 로컬이 아니라 DB가 맞아요. 로컬은 기기나 브라우저가 바뀌면 사라지고, 로그인 기능이 있는 서비스라면 계정별로 서버에 있어야 합니다.
  이전 채팅 기억의 원리: GPT API는 기억이 없어서 요청할 때마다 시스템 프롬프트 + 이전 메시지들 + 새 질문을 한꺼번에 보내야 해요. 그래서 "프롬프트랑 넣고?"의 답은 네, 같이 넣습니다. 대화가 길어지면 최근 N개만 보내거나 요약해서 보내는 식으로 줄이고요. 다른 대화방까지 기억하는 장기 기억은 나중 단계로 미루는 게 좋습니다.
  SSR: 벨로그형 글은 검색 노출 때문에 서버 렌더링이 유리하고, 채팅 화면은 실시간 응답(스트리밍)이 중요해서 클라이언트 쪽에서 처리합니다. 한 프로젝트 안에서 화면마다 다르게 쓰면 돼요.
  인증 방식(세션이나 JWT, Auth.js 같은 라이브러리 사용 여부)은 미리 하나 정해두세요.

  5. 스켈레톤 코드 (메모에 쓴 방향이 맞아요)
  먼저 폴더 구조, 인증 뼈대, 타입 정의(위의 컬렉션 구조 그대로), 공통 컴포넌트(헤더, 버튼, 입력창)를 만들고 시작하면 나중에 충돌이 훨씬 적어요. 이걸 만들려면 2번과 3번이 먼저 있어야 합니다.

  스프레드시트는 이렇게 만들면 좋아요

  탭 4~5개면 충분합니다.

  기능 목록: 기능 / 우선순위 / 담당 / 상태
  데이터 설계: 컬렉션 / 필드 / 설명
  페이지·API: 경로 / 역할 / 필요한 데이터
  결정 사항: 질문(예: 채팅 저장) / 결정 / 이유
  일정: 주차별 목표
  ```

### 11시 : 파트별 기능 정의 (로그인·회원가입)

- 협업 툴 : 구글 드라이브, 스프레드시트, 디스코드, 줌
- 휴식 후 파트별로 디스코드 채널에 흩어져 작업을 시작했다. 나도 같은 오쓰를 맡은 팀원과 음성·화면 공유로 논의하며 작업했다.
- 처음엔 조금 헤맸지만 크게 **로그인, 소셜 로그인, 회원가입, 소셜 회원가입, 마이페이지**로 나누고, 그 안의 파츠를 상세히 나눴다.
- 강사님 수업에서 만들었던 로그인·회원가입 페이지를 기반으로, 우리 프로젝트에 필요한 기능이나 넣고 싶은 기능을 추가했다.
- 4일짜리 짧은 프로젝트라는 걸 염두에 두고 구현 중요도를 3단계로 나눴다.
- 대화 중 마이페이지도 우리가 구현한다는 이야기가 나와서 내용을 구체화했다. 최종적으로 기능정의서 초안은 크게 로그인, 회원가입, 마이페이지 기능으로 정리했다.

### 1시 : 전체 공유와 목업

- 점심 후 팀원 모두 모여 11시까지 작업한 것을 이야기했다. 파트별로 기능을 어떻게 나눴고 어떤 기능이 필요한지 설명하고, 서로 겹치는 기능 이야기도 했다.
- 그런데 서로 설명하는 기능이 상상이 가지 않아 두루뭉술해진다는 느낌을 받았고, 팀원들도 마찬가지인 듯했다. 대화로 시간이 늘어지는 게 느껴졌다.
- 눈으로 보이는 게 있으면 팀원들이 설명하고 싶은 게 무엇인지 더 명확히 말할 수 있을 거라 생각했다. 그래서 각 파트가 준 기능 정의를 AI에게 주어 간단한 목업을 만들게 하고 공유했다.
  - 뼈대만으로 만든 목업이라 팀원분들 생각과 다르게 AI가 구현했을 거라 생각했다. 그 차이를 보며 각자 원하는 기능이 어떻게 나와야 하는지 시각적으로 다른 파트분들이 새롭게 목업을 만들어 오시거나 스키마를 가져오셔서 같이 설명해 주실 거라 기대했다.
  - 💭 그런데 우리 집 클로드가 생각보다 잘 만들었는지..? 몇몇 팀원분들이 내가 모르는 무언가를 깨달으신 것 같았다. 어떻게 된 일인지 잘 모르겠다. 내가 원한 방향은 아니었지만 뭔가 된 것 같기는 하다.
- 이후 다시 파트별로 나뉘어 생각을 정리했다.
  - 회원가입·로그인은 강사님이 강의해 주셨던 부분이라 추가 논의가 많이 필요하지 않아, 마이페이지 이야기를 좀 더 나눴던 것 같다.
  - 같은 파트 팀원분도 무언가에 집중하고 계셔서, 나는 기능정의서와 스키마를 AI 도움 없이 써 볼까 고민하며 썼다 지웠다를 반복하다 시간이 흘렀다.

### 2시 30분 : 다시 전체 상의

- 다시 모든 팀원이 모여 상의했다. 이때쯤부터는 다들 무언가 명확하게 정해진 게 있어 보였다.
- 하지만 스키마와 기능정의서는 여전히 비어 있었다. 막상 쓰려니 다들 같은 출발점에 있는 학생들이라 어려웠던 것 같다.
- 💭 나도 어려웠다.. 스키마가 어렵다는 말에 가장 경험 많은 분이 친절히 설명해 주시긴 했지만, RDB만 경험해 봤지 JSON이나 NoSQL은 이번에 공부하며 친숙해졌다 해도 여전히 생소해서 건드릴 엄두가 나지 않았다.

### 3시 40분 : 파트별 작업 시작

- 논의로 시간이 많이 걸려, 3시 40분부터 일단 파트별로 시작해 보기로 하고 흩어졌다. 이후 1시간 동안 각자 브랜치를 내어 일을 시작했다.
- 강사님 수업 방식을 그대로 따라가는 건가 싶어, 별도 브랜치에서 아토믹 방식 폴더를 빈 폴더로 먼저 만들어 커밋했다. 그 뒤 내 브랜치로 들어와 내가 맡은 부분을 본격적으로 생각하기로 했다.
- 내 담당은 로그인/회원가입이고, 마이페이지는 다른 분이 맡으셨다. 그분이 여행을 가시게 되어 한 페이지를 구현해 보시는 걸로 이야기를 마쳤다.
- 강사님을 따라 로그인 기능부터 구현하려 했지만, 사전 준비, 교안 작성, 어떻게 시작할지에 대한 고민이 많아 실제로 많은 걸 하지는 못했다.
