## 1. 디자인 적용 (새벽~9시)
**무엇을 확인하려는가** : 목업 그대로였던 화면을, 팀 코드를 크게 흔들지 않고 정돈된 디자인으로 바꿀 수 있는가

**한 일**
1. 디자인 시안을 적용할 브랜치를 `design/suggest`로 만들고 에이전트에게 작업을 맡겼다.
2. 커밋 6개로 나눠 올렸다. 디자인 토큰(색·간격을 한곳에 모은 `components/design/tokens.css`)·SUIT 글꼴·게시판 스킨, 공통 헤더와 계정 메뉴, 게시판용 CSS 부품, 채팅 화면, 인증 화면 디자인 통일, 마이페이지·유저 검색의 중복 버튼 정리.
3. 채팅은 기존 채팅 부품과 **같은 props**를 받는 디자인 버전을 만들어 바꿔 끼웠다.
4. 아침에 팀원분들께 보여 드렸고, 통과되어 PR #54로 머지했다.

## 2. 발표 준비 (발표 전)
**무엇을 확인하려는가** : 발표자분이 내 파트(인증·마이페이지)를 정확하게 말할 수 있게 대본과 슬라이드를 맞출 수 있는가

**한 일**
1. 발표자분의 대본에 두 가지를 더하고 싶었다. 이메일 관련 일이 어디서 일어나는지, 그리고 비밀번호와 인증을 따로 두는 이유.
2. 처음엔 "이메일 부분은 MongoDB에서"라고 생각했는데, 코드를 확인하니 반만 맞았다.

| 하는 일 | 어디서 |
|---|---|
| 아이디 → 가입 이메일 찾기 | MongoDB |
| 로그인 성공 뒤 같은 이메일로 회원 연결 (없으면 생성, upsert) | MongoDB |
| 아이디 찾기 (가입 이메일·복구용 이메일) | MongoDB |
| 아이디·닉네임 중복 확인 | MongoDB |
| 이메일 중복 확인 | Spring |
| 로그인 (이메일 + 비밀번호 확인) | Spring |
| 비밀번호 재설정 메일 | Spring |
| 비밀번호 변경 | Spring |

3. 나눈 이유는 두 가지로 정리했다. 첫째, 비밀번호 같은 민감한 정보는 한 곳에서만 다룬다. 그래서 우리 DB에는 비밀번호를 저장하지 않는다. 둘째, 서비스 데이터(아이디, 프로필, 글, 마이페이지 설정)는 인증 서버를 건드리지 않고 바꿀 수 있다. 솔직한 출발점은 Spring 인증 서버를 강의에서 제공받았다는 것이다.
4. 발표 자료는 전부 합쳐 5장, 우리 파트는 1장이었다. 슬라이드를 코드와 대조해 보니 틀린 내용은 없었고, 쉼표 앞 띄어쓰기나 "재설정 → 비밀번호 재설정" 같은 작은 표현만 제안했다.
5. 우리 조 발표 중에, 내 파트에서 나올 만한 질문과 한 줄 답을 준비했다. 가장 나올 법한 것은 "왜 DB를 두 개로 나눴나", "두 DB는 어떻게 연결하나", "토큰은 어디에 저장하나" 셋이었다.

## 3. 조별 발표에서 배운 것
**무엇을 확인하려는가** : 같은 과제를 다른 조는 어떻게 풀었고, 강사님은 무엇을 보시는가

| 조 | 서비스 | 기억에 남은 것 |
|---|---|---|
| 2조 | 소소스터디 (공부 스터디원 모집) | 주소창으로 원하는 지식·스터디를 쉽게 찾게 함. 코딩 명령어를 치면 반응하는 홈 배너. 서비스 화면 소개 위주 |
| 5조 | 학습 커뮤니티 데일리 피드 | 어떻게 만들었는지, 랜딩 화면, 핵심 코드 위주 |
| 4조 | 우리 조 | 아래 4장 |
| 6조 | | 선택과 집중, 실무자가 있던 조. 넥스트와 리액트 쿼리를 조합, 노드로 백엔드 같은 일, 유튜브 API. 작지만 완성도가 높음 |
| 3조 | SNS | 프론트 경험자 전무. 강사님의 조언에 따라 충실하고 완성도 있게 구현 |
| 1조 | 일조의 레시피 (레시피 앱) | 무조건 로그인해야 하는 앱이라, 한 번 로그인 후 여러 화면을 쓰기 편한 리액트를 채택. 넥스트와 리액트를 비교하기 좋은 프로젝트 |

**강사님이 짚어 주신 것**
- 만들어진 API로 버티다 도저히 안 돼서 백엔드에 부탁
- 강사님 경험담 : 프론트 초기에 400번대 에러(프론트가 할 일)를 백엔드에 해결해 달라고 했다가 부끄러웠던 적이 있다. 그래도 백엔드에 요청할 건 요청해 보아라. 경험해야 실력이 는다.
- 백엔드는 충돌이 잘 안 나는데 프론트는 잘 난다. 충돌 없이 해결한 것도 훌륭하다.
- 개발자 도구의 네트워크 창을 열어, 렌더링된 모습들을 많이 비교해 보기.
- 그간 공부하고 프로젝트한 경험으로 좋은 취업을 하길 바란다.

## 4. 우리 조 발표와 강사님 리뷰
**무엇을 확인하려는가** : 우리가 만든 서비스가 밖에서 보면 어떤가

**들은 것**
- 강사님이 실제 개발 화면과 채팅을 직접 해 보시고 질문도 해 보셨다. AI가 느린 것 빼고는 괜찮았다고, LG에 문의해 보라고 하셨다.
- 강사님 코멘트
  - 표현하는 것에 신경 썼다.
  - 보안 정책에 신경을 많이 써야 했을 텐데 노력한 것 같다.
  - 완성도도 높다.
  - 토큰을 모아서 관리하거나 처리하는 방식에 신경을 썼다.
  - 좋은 예도, 안 좋은 예도 있다.
- 강사님이 AI로 뽑은 코드 리뷰를 잠깐 보여 주셨다.

  | 구분 | 리뷰 내용 | 관련 |
  |---|---|---|
  | 완성도 | 채팅, 게시판, 회원, 계정 찾기가 빈 페이지로 끝나지 않는다 | |
  | 좋은 예 | `app/layout.tsx`가 `lang="ko"`. `components/design/tokens.css`로 색·간격을 토큰으로 모으는 중 | 새벽에 붙인 디자인 토큰 |
  | 나쁜 예 | 게시판이 `/api/board` 전체를 받아 화면에서 8개씩 자른다. 검색어가 주소에 남지 않아 새로고침하면 필터가 사라진다. 글이 늘면 첫 응답과 메모리가 같이 커진다 | 다시 볼 곳 : searchParams (10/30·11/03) |
  | 설정 | `npm ci`의 postinstall이 `prisma generate`를 돌려서, `DATABASE_URL`이 없으면 설치가 실패한다. 루트 레이아웃이 `./posts/board.css`를 모든 화면에 넣어, 채팅과 로그인도 게시판 스타일을 받는다 | 새벽 디자인 커밋도 `board.skin.css`를 루트 레이아웃에 넣었다 |

- 강사님께서 잘 만들었다고 말씀해주셨다. 디자인도 신경 써서 좋았다고 해 주셔서 기분이 좋았다. 모바일 화면도 구현해두었는데 괜히 생색내는 것 같아 조원분들께 말하진 않았지만.. 아마 강사님은 보셨기에 그런 말을 해주시지 않았을까 기대해본다.

## 5. 발표를 보며 다시 본 우리 코드
**무엇을 확인하려는가** : 다른 조 슬라이드의 "브라우저로 가는 순간 털린다"(강의 10/29)를 우리 코드도 지키고 있는가

**한 일**
1. 다른 조 슬라이드는 "토큰은 서버만 읽는 암호화 쿠키에, `session()`에는 토큰을 넣지 않는다"였다. 우리 코드와 대조했다.

| 확인한 것 | 우리 코드 | 결과 |
|---|---|---|
| Spring 토큰 위치 | `lib/authOptions.ts`의 `jwt()`에서 `token.springAccessToken`에만 넣음 | 브라우저로 안 감 ✅ |
| `session()`에 넣는 것 | Spring 토큰은 빠져 있음 | ✅ |
| 토큰을 붙이는 곳 | 비밀번호 변경·로그아웃에서 서버가 쿠키에서 꺼내 씀 | ✅ |
| 우리가 만든 앱 토큰 | `session.accessToken`이 `AuthShell.tsx`에서 클라이언트로 넘어가고, `/api/auth/session` 응답에도 들어 있음 | 브라우저로 감 ⚠️ |

2. 앱 토큰은 받아 주는 곳이 없어서(헤더를 읽는 우리 API가 없고, proxy는 쿠키만 확인) 위험은 낮다. 안에 든 회원 번호·이메일·이름도 원래 세션 응답에 있는 정보다.
3. 그래도 브라우저에서는 로그인 여부(`Boolean(accessToken)`)를 판단하는 데만 쓴다. 다음에는 토큰 대신 true/false만 주고받고 싶다.
