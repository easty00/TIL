## 4강 : Branch의 개념과 활용

#### 과거로 돌아가기 이어서
- reset : 원하는 시점으로 돌아간 뒤 이후 내역들을 지우는 것
  - 과거로 돌아갈 땐 반드시 해시 값을 가지고 있어야 한다
  - 실습은 혹시모를 대참사를 대비해 하지 않을 예정. 수업 메모만 한다.
  ```
  돌아가려는 커밋의 해시값을 복사
  git reset --hard (해시값) 
  ```
  - git log로 확인해보면 되돌아간 해시 값 이후의 커밋들이 사라진다
  - 백업한 깃 폴더를 다시 가져오면 되돌릴 수 있다(백업 전제)
  ```
  백업한 폴더를 가져온 후
  git reset --hard
  ```
  - 뒤에 해시값을 작성하지 않는 경우 마지막 해시값 상태로 되돌리는것으로 인식한다.

- revert : 되돌리기 원하는 시점의 커밋을 거꾸로 실행하는 것
  ```
  git revert (해시값)
  ```
  - 무언가 편집기가 나오고 수정했다라고 표시됨.
  - :wq <<를 입력하여 저장
  - sourcetree를 새로고침하면 revert 가 붙은 이전 커밋 메시지가 나오는 것을 볼 수 있다.
  - revert 중에 충돌이 났을 때 사용  
    ```
    git revert --continue
    ```
  - 리버트 기록 원복
    ```
    git revert --no-commit (해시값)
    git reset --hard
    ```

### 브랜치
- 분기된 다른 차원(공간)
- 특정 프로젝트를 분기하여 작업할 때 사용. 제각각 브렌치마다 독립되어 진행할 수 있고, 통합할 수 있다.
- 생성
  ```
  git branch 브랜치명
  ```
- 이동
  ```
  git switch 브랜치명
  ```
  - 브랜치 생성과 동시에 이동
  ```
  git switch -c 브랜치명
  ```
- 삭제
  ```
  git branch -d 브랜치명
  ```
- 브랜치명 수정
  ```
  git branch -m (기존 브랜치명) (새 브랜치명)
  ```
- 브랜치 강제삭제(주의!)
  ```
  git branch -D 브랜치명
  ```

## 6강 : Github 연동 및 원격 저장소

### Merge 실습
- 두개의 브랜치 합치기
- 서로 다른 브랜치를 합치는 방식
  - merge : 두 브랜치를 한 커밋에 이어붙이는 것
    - 브랜치의 사용내역을 남길 수 있음
  - rebase : 브랜치를 다른 브랜치에 이어붙이는 것
    - 한줄로 깔끔하게 유지, 병합된 브랜치의 기록이 남지 않음

- main 브랜치에 다른 브랜치를 merge
  - 먼저 병합할 브랜치로 이동함.
  ```
  git switch main
  git merge (병합할 브랜치 명)
  ```
  - sourcetree 를 새로고침 하면 main에 다른 브랜치가 병합된 걸 확인할 수 있음

    ![merge1](./data/merge1.png)

  - merge 또한 하나의 커밋이기 때문에 리셋을 이용해 병합 이전 상태로 되돌릴 수 있다.
    - sourcetree 에서 커밋 되돌리기를 누르는 것으로도 가능하다.

  - 병합이후, 병합된 브렌치는 더 필요없게 되므로 삭제할 수 있다.
    ```
    git branch -d (브렌치 명)
    ```

    ![merge2](./data/merge2.png)

- rebase 를 이용하여 합치기. merge와 반대.
  - 주가 되는 브랜치가 아니라 병합되어질 브랜치로 이동하여 합친다

    ![rebase](./data/rebase.png)
    
    - merge와 다르게 해당 브렌치가 main보다 앞서있는 것을 확인할 수 있다. 따로 진행되어있던 main의 커밋 데이터가 add-team에 합쳐지면서 add-team의 개별 브랜치가 완전히 사라진 것을 확인할 수 있다.

- main으로 돌아오면 new-team의 데이터는 병합되어있지 않다.
  - new-team을 merge 하여 데이터를 가져오면 동일한 위치에 두개의 브랜치가 동일한 데이터를 가지고 존재하는 것을 확인할 수 있다.
  - new-team 브랜치도 더는 사용하지 않으므로 삭제할 수 있다.

## 7강 : Push & Pull 실습

### 브랜치 간 충돌이 일어나는 경우 수습하는 방법
- 새로운 브랜치를 만들어 충돌을 진행한다. 제각각 같은 위치를 수정한 파일 준비.

  ![merge3](./data/merge3.png)

- merge 후 충돌
![merge4](./data/merge4.png)
  - 병합 과정에서 충돌이 발생하고 당장 충돌 해결이 어려울 경우 merge 중단
    ```
    git merge --abort
    ```
  - 충돌을 해결한 경우
    ```
    git add 
    git commit -m
    ```

- rebase 후 충돌
  - 병합 과정에서 충돌이 발생하고 당장 충돌 해결이 어려울 경우 rebase 중단
    ```
    git rebase --abort
    ```
  - 충돌을 해결한 경우
    ```
    git add 
    git rebase --continue
    ```
- 이후 필요없는 브렌치 삭제

## 8강 : 협업 시나리오

### 깃허브에 프로젝트 올려서 활용하기
- Git : 코드의 버전을 관리하는 프로그램. 내 컴퓨터에서 동작하며 버전관리 브랜치 등의 작업 등을 담당
- GitHub: 깃을 사용하는 프로젝트를 저장하고 협업할 수 있는 하나의 클라우드 서비스

- 만든 프로젝트를 원격 저장소에 올리기
  - 깃허브에 로그인. vs코드를 깃허브와 연결
  - private repository : 개인 비공개 레포지토리
  - public repository : 공개 레포지토리. 이를 협업에 이용
  - vs코드 위 검색창에서 만들 수 있음.
  - 웹으로 들어가면 해당 프로젝트용 레포지토리가 만들어진 것 확인 가능. 

- 연결된 레포지토리 확인
  ```
  git remote -v
  ```

- 레포지토리 다운
  ```
  터미널을 열고
  git clone (레포지토리 주소)
  ```

- 원격 저장소인 레포지토리에 커밋 저장
  ```
  git push -u origin main
  git push
  ```

- 웹 페이지에서도 코드를 수정하고 저장할 수 있다.

- 프로젝트를 하다 보면, 원격에 다른 팀원이 진행상황을 저장하여 내가 가진 저장소와 달라질 수 있다.
  - 그럴 때 원격에 저장되어있는 정보를 확인한 뒤 받아오려면
  ```
  git fetch
  git pull origin main
  git pull
  ```
  - push, pull을 할 때 항상 저장소가 동기화된 상태를 확인하여야 충돌을 최소화 할 수 있다.

  - push 하려는데 원격의 동일 브렌치에 다른 별도의 커밋이 존재하는 경우 : rebase를 이용하면 안전하다
    ```
    git pull --no-rebase : 원격 커밋과 내 커밋을 병합 커밋으로
    git pull --rebase : 원격 커밋 뒤에 내 커밋을 다시 붙임
    git push
    ```
